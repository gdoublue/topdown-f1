## 1. 一页读懂

### 1.1 我们在解决什么

这是一款俯视角 F1 竞速游戏，支持 8 人同场在线对战（真人 + AI 补位）。**单机很顺、联机很抖**是这类游戏最典型的投诉，本轮工作的目标就是让 8 人同场时：

- 自己开的车永远顺（零网络延迟感）；
- 别人看到的你的车位置正确、过弯车头跟得上；
- 弱网/低端机出现时，能"平滑地降级"，而不是"抽搐 + 瞬移"。

### 1.2 最终结论

这一轮共定位并修复 **8 个可复现的观感缺陷**，**没有一个是"带宽不够"**：

| 类别 | 数量 | 典型现象 |
|---|---|---|
| 时钟不同源 | 3 | 自车"窜一下再被镜头追回"、AI 开局冲出赛道、位置比真实还靠前 |
| 基准跳变（时间轴被打断） | 2 | 定格几十毫秒再闪一下、整局永久偏老 → 一直外推 |
| 控制器自激（我们自己的补丁引入） | 2 | 高频抽搐、抖动在两侧来回迁移 |
| 权威校验误杀 | 1 | 单向卡顿：只有低帧率的那台机器"卡" |

立下的核心规矩是三条：

1. **自车与世界必须共用一个时钟**（物理推进的时间 = 画面推进的时间）；
2. **时间轴只允许平移，不允许跳变**（时钟修正一律走"整体平移 + 限速"）；
3. **每条链路只留一个旋钮**（禁止多个反馈回路改同一个播放点）。

### 1.3 修复后实测（同局两台机器）

| 机器 | 帧时间 `perf.frame` | 对端播放点领先量 `lead` | 是否在直线外推 `extrap` |
|---|---|---|---|
| Edge（60fps） | avg 15.9ms / max 21ms / 卡顿 0 | −72ms | 0 |
| Chrome（修复前） | avg 156.9ms（≈6fps）/ max **14575ms** | **+3705ms** | **1（长期外推）** |
| Chrome（修复后） | —— | 回到 −110 ~ −30ms | 0 |

Chrome 那一行就是"抽搐"的现场：播放点跑到真实位置前面 3.7 秒，只能一直直线外推。

## 2. 背景

### 2.1 产品与玩法

| 项 | 说明 |
|---|---|
| 视角 | 固定俯视（Top-down），Canvas 2D 绘制，Web Audio 引擎声 |
| 平台 | 浏览器（Chrome / Edge / Firefox），无插件；服务端 Node.js |
| 模式 | 单人计时（solo）、对战 AI（vs）、全 AI 观战（spectate）、**在线对战（onlinerace）**、在线练习 |
| 赛道 | 7 条（上海 5.45km/3 圈、蒙扎 5.79km/3 圈、银石 5.89km/3 圈、斯帕 7.00km/3 圈、红牛环 4.32km/4 圈、直线竞速 6.00km/1 圈、环形 4.50km/3 圈） |
| 车辆 | 7 台可配置车型 + 玩家自选，单房上限 8 人（不足用 AI 补位） |
| 特色 | 内置"自动驾驶算法沙盒"：玩家可以写 JS 算法接管自己的车（这也决定了反作弊必须存在） |

### 2.2 技术架构与部署拓扑

```
浏览器 A ─┐                        ┌─ WebSocket  /ws   （大厅/房间/开赛/成绩/信令，可靠有序）
          ├── nginx :8080 (TLS) ───┤
浏览器 B ─┘         │              └─ WebRTC DataChannel（位姿 snapshot/peer_state/car_state，UDP 无序不重传）
                    │                        ▲ STUN + UDP 40000-40100
                    ▼
            f1-server :8081 (Node 18, systemd)
                    ├─ 会话/房间/排行榜（JSON 落盘）
                    └─ 权威模拟：30Hz tick，AI 车物理 + 玩家幽灵状态
```

- 服务器：华为云 ECS，2 vCPU / 1.7GiB，Ubuntu 24.04；
- 入口用 **:8080**：域名首次指向大陆服务器后，80/443 被备案拦截，非 80/443 端口不受影响；
- `node-datachannel` 原生模块做 WebRTC 服务端；不可用时 `RTC=0` 整体回落 WebSocket。

### 2.3 权威模型：三种实体，三套规则

| 实体 | 位置由谁算 | 为什么这样设计 |
|---|---|---|
| **自车（本地玩家）** | 客户端本地完整物理（与单机同一套 `stepCar`） | 手感零延迟；输入→画面不经过任何网络往返 |
| **其他真人（幽灵）** | 对方客户端算，通过服务端中继 | 8 人互相模拟成本高且无法收敛；"各算各的"避免互相顶牛 |
| **AI 补位车** | 服务端权威模拟（30Hz） | 所有客户端看到完全一致的 AI 轨迹 |

代价：服务端必须对客户端上报的坐标做**合理性校验**（否则改内存就能瞬移拿第一），而这类校验非常容易"误杀合法数据"——第 4.2 节的 P0 故障就是这么来的。

### 2.4 实时竞速为什么难：四个物理约束

| 约束 | 本项目的实际数值 | 后果 |
|---|---|---|
| **延迟** | 同城 5~20ms，跨网 30~80ms，企业网/4G 100ms+ | 看到的是"过去的对方"；延迟必须被"播放缓冲"吃下去 |
| **抖动** | 主线程一忙就能测出 25~56ms 的假抖动；真实链路 1% 概率 180ms 尖峰 | 缓冲不够就会"外推→定格→瞬移" |
| **丢包 / 队头阻塞** | TCP 下"一包迟到 180ms"会让后面所有包一起迟到 | 这就是改用 WebRTC DataChannel（UDP）的直接原因 |
| **客户端性能** | 实测同一局两台机器：60fps 与 **6fps**（还卡死过 14.5 秒） | 低帧率端上报稀疏、时间戳断层，能拖垮所有人的观感 |

再加两个本项目特有的约束：

- **玩家可自定义算法**（自动驾驶沙盒）→ 位置必须可信，校验不能删；
- **同屏 8 车 + F1 电视转播 HUD + 大画布** → 主线程本来就紧张，网络逻辑必须"很轻"。

### 2.5 设计目标与取舍

| 目标 | 取舍 |
|---|---|
| 手感优先 | 自车完全本地权威，宁可牺牲"绝对公平"，也不让输入有延迟 |
| 位置可信 | 服务端校验只用"物理上可能的速度上限"，不重建玩家物理 |
| 平滑优先于实时 | 远端车统一延后播放（80~150ms，慢对端最多 +300ms）：宁可看"略旧的残影"，也不要抖 |
| 可降级 | UDP 不通回落 WS；缓冲不够自动加深；对端失联分档（半透明 → 消失） |

### 2.6 名词表（便于外部读者）

| 术语 | 解释 |
|---|---|
| rAF | `requestAnimationFrame`，浏览器每帧回调；窗口被遮挡时会被节流到 1~2Hz |
| 播放缓冲 / playout buffer | 把收到的位姿先"压一段时间"再播放，用这段延迟吸收抖动（类似视频缓冲） |
| 外推 / dead reckoning | 缓冲被掏空时，按最后已知的速度和航向"直线推测"位置 |
| 采样时间戳 `st` | 发送端给每个位姿样本打的本地单调时钟时刻 |
| 时钟偏移 `off` | `off = min(到达时刻 − st)`，把对方的时钟换算到本机时间轴（最小延迟滤波） |
| 幽灵模型 | 玩家之间不互相模拟物理，只在本地做视觉/碰撞响应，成绩由服务端校验 |
| 队头阻塞 | TCP 有序性导致"前一包迟到 → 后一包必须等"，UDP 没有这个问题 |

## 3. 系统设计（最终形态）

### 3.1 传输分层

| 数据 | 通道 | 语义 |
|---|---|---|
| 大厅 / 房间 / 开赛 / 成绩 / RTC 信令 | WebSocket | 可靠、有序、低频 |
| `snapshot`（服务器→客户端，30Hz） | DataChannel | `unordered` + `maxRetransmits:0` |
| `peer_state`（客户端→服务器→其他客户端，60Hz 中继） | DataChannel | 同上 |
| `car_state`（客户端上报自车位姿，60Hz） | DataChannel | 同上 |

建链失败 / UDP 被墙 / STUN 不通 → 自动全程回落 WS，业务层完全无感。诊断：`__gp.conn.transport`。

### 3.2 三层时钟

```
① 服务器 tick 逻辑时钟 ts（每 tick 严格 +33.3ms，与任何人帧率无关）
        │   srvOff = min(recvAt − ts)，热机后冻结
        │   偏移变化时：参考轴 shiftRef + 所有缓冲样本 rebaseBuffer（同一平移量）
        ▼
② 本机播放时钟 renderMs（速率 1.0；偏差超出死区才用 ≤±4% 修正）
        │   playMs = renderMs − offsetMs       （offsetMs：全局自适应延迟 0~70ms）
        ▼
③ 每车播放点 entryPlayMs = playMs − extraMs  （extraMs：每车独有 0~300ms）
        │
        ▼
④ sampleRemote()：Catmull-Rom 样条插值（关键帧处速度连续）
                   仅在对端安静时航位推算，上限 min(250, 30 + 静默时长) ms
```

**为什么要有 ①**：真人样本的间隔天生不均匀（15~79ms），若让样本推动时钟，AI 车也会被带得一起抖。所以时钟只认服务器 tick 这条**均匀轴**，样本只被插值。

**为什么要有 ③**：每个对端的到达情况不同（帧率、上行、主线程），全局只调一个延迟要么不够、要么把全场的滞后一起抬高。每车独立一个"额外延迟"，只影响那一辆车。

### 3.3 样本时刻的两种来源

| 实体 | 时间戳来源 | 换算 |
|---|---|---|
| AI 车 | 服务器 tick 逻辑时钟（与 ① 同源） | 直接用，绝对均匀 |
| 真人 | 对方本机 `performance.now()` | 该实体的 `off = min(recvAt − st)` 换算到本机 |

AI 用服务器时钟、真人用对方时钟，两套时间戳互不干扰——这是"AI 永远丝滑，真人需要缓冲"的根源。

### 3.4 每车播放缓冲的控制律（最终版）

```
lead = 播放点 − 最新样本时刻          （负值 = 还在样本后面，正值 = 已在替他外推）

下限（只抬不压）：extraMs ≥ 覆盖一个采样间隔所需
   floor = gap × 1.25 − (全局延迟 − 20ms)

死区控制（用 lead 的 EWMA，避免被 16.7ms 的样本阶梯带抖）：
   lead > −30ms   → 往后垫延迟（≤240ms/s，连续变化）
   lead < −110ms  → 才允许慢慢收回（≤60ms/s），且不低于 floor
   中间           → 什么都不做
```

目标不是"lead = 0"（那必然在样本边界上来回切），而是**稳定待在 −110 ~ −30ms**：永远走插值，绝不碰外推。

### 3.5 六个不变式（违反就出故障，都是踩过坑立的）

| 不变式 | 违反后的现象 |
|---|---|
| 偏移一变，**参考轴 + 已缓冲样本**平移同一量 | 新样本比旧的还早 → 被丢弃 → 定格几十毫秒再闪一下 |
| 上报时间戳 = **真实时间**，不是"补推后的模拟时刻" | 卡死一次 → 时间戳出现年代断层 → 锁相被污染 → 长期外推 |
| 每车只有 `extraMs` 一个旋钮，且带死区 | 多回路抢同一个量 → 高频抽搐，且抖动会在两端来回迁移 |
| 比赛状态单向推进 | 乱序旧快照让物理少跑一帧 → 冻一帧再弹 |
| 一帧只上报一次，且只在最后一个物理子步 | 同刻样本被合并 → 坐标跑在时间戳前面 → 看着"提前" |
| 物理补推只在最后一步解算碰撞 | 掉帧越狠被 -45% 速度差连罚越多次 → 一顿一顿 |

### 3.6 带宽与开销预算（单房 8 人）

| 项 | 估算 | 说明 |
|---|---|---|
| `car_state` 上行 | 60Hz × ~150B ≈ **9KB/s/人** | 只在 UDP 可用时；WS 回落同量 |
| 位姿下行（合包） | 60Hz × ~600B ≈ **36KB/s/人** | 8 人房：服务端发送 3360 次/秒 → **≈60 次/秒** |
| `snapshot` 下行 | 30Hz × ~1KB ≈ **30KB/s/人** | 整房只序列化一次（8 人房：序列化 240 次/秒 → 30 次/秒） |
| 服务端 CPU | 30Hz tick + 8 车物理 + 快照 | 2 vCPU 可跑多房；单房实测 CPU 占比很低 |

> 位姿下行原先是"收到一个 `car_state` 立刻转发给其他每个人"（8 人房 480 包/秒 → 3360 次发送/秒）。
> 客户端本来就有 80~150ms 播放缓冲，省那几毫秒中继等待对画面没有意义，因此改为
> **每 16ms 把房间内所有幽灵的最新位姿打成一个包广播**（`peers_bundle`），发送次数降 98%。

## 4. 故障案例集

> 每个案例按"现象 → 复现 → 数据 → 根因 → 修复 → 验证 → 教训"展开，便于复盘与对外讲解。

### 4.1 案例 ①：自车"一顿一顿"，车不连贯【P0】

**现象**：在线对战里，连自己开的车都显得断续；单机模式完全正常。

**复现**：多开两个浏览器、或让窗口半遮挡（帧时间掉到 30~60ms）。

**根因**：两个时钟。

| 谁 | 用的时间 | 上限 |
|---|---|---|
| 自车物理 | `performance.now()` 真实间隔（可由 16ms 定时器推进） | 250ms/帧 |
| 镜头 / 粒子 | rAF 的 `dt` | **50ms，且不含定时器推进的那段** |

掉一帧（>50ms）时，车按真实时间前进 3~12m，镜头只追 50ms 的量 → 车在屏幕上先窜一段，再被指数缓冲（时间常数 ~0.24s）拽回来。

**放大因素**：补推把一帧拆成 2~8 个物理子步，而 `update()` 内部含"非对称碰撞"（撞到远端车时每步 -45% 速度差 + 位移硬分离 + 镜头抖动 +3）→ 补 3 步就被罚 3 次。

**修复**：

```js
// 累计"两次绘制之间实际推进的模拟时间"，镜头/粒子一律用它
advanceNetSim(now);
visualDt = netSimAccum > 0 ? Math.min(0.25, netSimAccum) : dt;
netSimAccum = 0;
updateCamera(activeCar, visualDt);

// 碰撞只在最后一个子步解算
for (let i = 0; i < steps; i++) update(stepDt, i === steps - 1, nowMs);
```

另两处：`lastRafAt` 改用回调真实开始时刻（否则 30fps 的机器会被误判为"rAF 停摆"）；新增 `__gp.perf` 暴露帧间隔与模拟/画面推进时间。

**验证**：`__gp.perf.sim.gapMs ≈ sim.visualMs`（两者同源）。

**教训**：只要有两处代码各自"按时间推进"，就一定会分叉。慢的一方会变成"落后的那个"，在画面上表现为抖动。

### 4.2 案例 ②：Edge 看 Chrome 的车卡，Chrome 看 Edge 正常【P0】

**现象**：**单向**卡顿。同一局、同样代码，只有帧率不稳的那一侧"卡"。

**数据**：服务端日志显示该会话 UDP 双向收发正常（上行 11204 包，丢弃 0），排除链路问题。

**根因**：服务端反作弊窗口用"到达间隔"算位移上限。

```js
const dt = (now - g.lastAt) / 1000;        // 到达间隔
const stepLimit = vMax * dt * 1.5 + 2;     // 正常 60Hz ≈ 2m 余量
if (jump > stepLimit) { g.rejected++; }    // 位置原地不动，但 st 继续前进
```

客户端掉帧后会把物理**补推**一段（一帧最多 250ms），这批位移在真实时间上完全合法；但补推样本常常"成串到达"，到达间隔只剩几毫秒 → 窗口只有 ~2m → 判成瞬移。

后果不是"玩家被拦住"，而是**别人收到的数据变成"时间在走、坐标不动"** —— 接收端拿到同坐标、新时间戳的重复样本，画面一格一格地卡。帧率越低越容易命中，于是"慢的那台机器卡"。

**修复**：窗口基准改用**发送端自报的 `st` 差**（这才是这段位移对应的真实时长），并用到达间隔 `+0.35s` 封顶防伪造：

```js
const stDt = stNow > stPrev ? Math.min(2, (stNow - stPrev) / 1000) : 0;
const dt = Math.max(arrivalDt, Math.min(stDt, arrivalDt + 0.35));
```

顺带修好了里程 `rd` 被同一窗口卡住的问题。

**教训**：反作弊校验的"时间基准"必须与"位移的产生方式"一致。客户端补推是合法行为，校验要按客户端的真实经过时间算，而不是按服务端看到包的间隔算。

### 4.3 案例 ③：开局约 2 秒，AI/电脑车集体冲出赛道又回来【P1】

**现象**：绿灯后约 2 秒，所有 AI 车沿直线冲出赛道，随后被拽回赛道；人类车不受影响。

**时间点的意义**："2 秒"正好是 WebRTC DataChannel 接管、链路延迟骤降几十到上百毫秒的时刻。

**根因**：参考轴只吃历史最大值，样本却用当前偏移。

```js
const srvOff = srvClock.observe(recvAt, msg.ts);
if (hasTs) clock.noteRef(msg.ts + srvOff);   // noteRef 内部只取 max
```

`srvOff` 变小（链路变好）→ 新样本时刻整体前移 → 但 `refMs`（参考轴）停在旧的大偏移上 → **播放点永久跑在最新样本前面** → 只能按航向外推。拐弯处的外推就是"直线冲出赛道"，新样本到了再被拽回来。

**修复**：偏移一变，参考轴同步平移（单次封顶 180ms，避免落进"偏差 >300ms 直接对齐"的硬分支）：

```js
if (lastSrvOff != null && srvOff !== lastSrvOff) {
  const dOff = Math.max(-180, Math.min(180, srvOff - lastSrvOff));
  clock.shiftRef(dOff);
  for (const e of entries) rebaseBuffer(e.buf, dOff);   // 缓冲必须同步平移
}
lastSrvOff = srvOff;
```

**教训**：时钟偏移会随链路变化，"历史最大值"和"当前值"混用，等价于在两条时间轴上取数据。

### 4.4 案例 ④：Edge 看 Chrome 的车"比真实位置还靠前"，过弯车头不转【P0】

**现象**：位置提前，且过弯时车头保持进弯前的朝向。

**关键判据**：**朝向不转 = 一定在走外推分支**。外推代码里角度是固定值：

```js
// 旧版
return { x: last.x + cos(last.a) * last.v * dtSec, a: last.a, extrapolated: true };
```

**根因**：补深判据选错了。

```js
const needExtra = gap * 1.25 - Math.max(30, clock.delayMs - 20);   // 只看采样间隔
```

对端是 60Hz、采样间隔完全正常 → `needExtra` 恒为 0 → **哪怕它的包到得慢（主线程卡 / 上行慢），也一毫秒缓冲都不加** → 播放点常年越过它的最新样本。

**修复**：

1. 补深判据换成**领先量** `lead = 播放点 − 最新样本时刻`（直接度量"我是不是已经在替他外推"）；
2. 外推上限随"对端安静了多久"连续放开：`min(250, 30 + netAge)`；
3. 外推时角度也按横摆角速度外推（由最后两个样本估算，±3 rad/s 限幅），避免"车头不转"。

**教训**：选反馈量要选"结果"，不要选"代理指标"。采样间隔正常 ≠ 数据按时到。

---

### 4.5 案例 ⑤：位置对了，但开始"抽搐、一闪一闪"【P0】【自伤】

**现象**：上一版修复上线后，高频抖动（一闪一闪）。

**根因**：修复 4.4 时写成了**开关控制**：

```js
if (lead > 0) e.extraMs = Math.min(450, e.extraMs + Math.min(lead, 24));  // 每帧最多拽回 24ms
```

三个效应叠加：

1. 每帧拽回最多 24ms（≈1.2m @ 180km/h），下一帧又被按采样间隔算的回路推回去 → ±20ms 的极限环；
2. 播放点压在样本边界上 → `extrapolated` 在开/关之间频繁切换；
3. 每次切回都执行"外推回弹补偿" `recX += (c.x − tx)`，上限 **25m** → 每两帧注入一次误差再指数衰减。

另外外推上限当时写成 `age < 150 ? 40 : 250` 的**硬切换**，切换的那一帧目标点会一次前跳 8 米，本身也是一次"闪"。

**修复**：

```js
// 死区控制：目标区间 [-110, -30]，中间什么都不做
e.leadEwma = e.leadEwma ? e.leadEwma * 0.88 + lead0 * 0.12 : lead0;
if (e.leadEwma > -LEAD_NEAR_MS) e.extraMs += Math.min(e.leadEwma + LEAD_NEAR_MS, 240 * dt);
else if (e.leadEwma < -LEAD_FAR_MS) e.extraMs -= 60 * dt;

// 外推上限连续化
const res = sampleRemote(buf, entryPlayMs, Math.min(250, 30 + netAge));

// 回弹补偿只对"连续外推 > 30ms"生效，上限 8m
```

**教训**：任何"每帧修正一点"的回路都必须带死区和速率上限，否则它自己就是抖动源。

### 4.6 案例 ⑥：症状反向迁移——Chrome 看 Edge 开始抽搐【P0】

**现象**：同一套代码，抖的位置从一侧换到另一侧。

**根因**：不是某一行写错，而是**三个独立回路改同一个播放点**，谁处在阈值边上谁就抖；同时有两个放大器：

- 时钟偏移的**重锁门槛只有 80ms** → 主线程一忙（个别包"看起来早到"）就重锁 → 时间轴被反复平移；
- 末级平滑 **12ms**（每帧吃掉 75% 偏差）→ 把不可控的到达抖动直接透到画面。

**修复（"收敛"轮）**：

| 改动 | 数值 |
|---|---|
| 偏移重锁门槛 | 80ms → **300ms**（只认真实异常：换链路/重连） |
| 偏移变化时 | 已缓冲样本**整条平移**（`rebaseBuffer`） |
| 每车旋钮 | 合并为 **1 个**（`extraMs`），下限只抬不压、消抖只在死区外动 |
| 末级平滑 | 人类 12ms → **25ms**，角度 14ms → **30ms**（约 1.2m 滞后换平滑） |

**教训**：每加一个反馈回路，都要问"它和现有的谁抢同一个旋钮"。答案若是"同一个"，就必须合并。

### 4.7 案例 ⑦：`lead 3705ms / extra 顶满 / extrap 恒 1` —— 时间轴年代断层【P0】

**数据（现场）**：

```json
{ "avgMs": 156.9, "maxMs": 14575.5, "hitches": 3 }
{ "delayMs": 150, "offsetMs": 70, "starved": true,
  "cars": [{ "id": "sid_9a56…", "gap": 21, "extra": 450, "lead": 3705, "extrap": 1 }] }
```

**含义**：那台机器 ≈6fps，并且**卡死过 14.5 秒**；播放点跑到最新样本前面 3.7 秒，延迟顶满、长期外推。

**因果链**：

1. 卡死 14.5 秒 → 补推钳制"一帧最多补 250ms"（这是对的，避免物理积分爆掉）；
2. 但当时**样本时间戳用的是补推后的模拟时刻** → 时间戳序列出现 14 秒的断层；
3. 接收端 `off = min(recvAt − st)` 被断层污染，锁到一个偏小的值；
4. 此后这辆车的样本**永远偏老** → 播放点永远在前方 → 只能一直外推。

**修复**：

| 位置 | 改动 |
|---|---|
| 发送端 | 时间戳回到**真实时间**；一帧只上报一次（`finalStep`） |
| 接收端 | 时间戳倒退 >400ms → 重置该实体时间轴；前进 >800ms → 丢弃旧样本 |
| 接收端 | 偏移一次跳 >500ms → 重置该实体 |
| 接收端 | 看门狗：`lead > 500ms` 持续 0.5s → 重置该实体（几百毫秒自愈） |
| 接收端 | 每车延迟上限 450ms → **300ms**（再高只会永久落后并掩盖真实故障） |

**教训**：**时间戳的语义必须单一**。"样本所在的真实时间"和"模拟推进了多少"是两件事，混用会在卡死之后产生年代断层，而断层会被最小值滤波永久记住。

| 参数 | 值 | 调大的后果 | 调小的后果 |
|---|---|---|---|
| `SAMPLE_HZ` | 60 | 带宽↑，接收端缓冲需求↓ | 远端播放必须更深，过弯更"棱角" |

| `HISTORY_MS` | 700 ms | 内存/遍历成本略增 | 采样点前移时会倒带 |
| 补推钳制 | 250 ms/帧 | 卡死后恢复快，但会瞬移一大段 | 卡死后进度永久落后 |
| `AI_HUD_INTERVAL_MS` | 80 ms（12.5Hz） | HUD 更跟手，但吃帧预算 | 计时数字更"跳" |
| `RENDER_DPR_MAX` | 1.5 | 更清晰，填充开销随面积平方增长 | 高 DPI 屏上略糊，但帧时间下降明显 |
| 幽灵碰撞动量冷却 | 150 ms | 轻微蹭碰更"实"，但贴车会连罚 | 连续贴车几乎无速度损失 |

调参原则：**先保证"永远在插值"**（`lead` 为负），再谈延迟；延迟只能通过"上限 + 速率"调整，不能跳变。

## 8. 方法论复盘

**做对的**：

1. **先分清"位置错"还是"朝向错"** —— 朝向不转必然在走外推分支，这条判据当场定位了 4.4；
2. **先量后改** —— 4.7 靠 `perf.frame` + `net.stats` 两组数字一次定位；而 4.5 是在没有数据时凭推理加的补丁，直接制造了下一个问题；
3. **诊断口提前埋** —— `__gp.perf` / `__gp.net.stats` / `__gp.net.jumps` 把"猜"变成"读"；
4. **每次修复都写下"不变式"** —— 后一轮改动能自查是否违反前面立下的规矩。

**做错的**：

1. 用"开关控制"修平滑问题（4.5），把一个抖动换成另一个抖动；
2. 一开始没有区分"到达抖动"和"时间轴故障"，导致两种完全不同的病因被同一套参数去调；
3. 一度让三条回路共用一个旋钮（4.6），使症状在两端来回迁移。

**下一轮的技术方向**（按收益排序）：

1. 把**模拟与渲染彻底解耦**：16ms 定时器固定 60Hz 推进，rAF 只负责画 —— 这样"低帧率端"也不会污染上报节拍；
2. ~~压每帧固定开销：HUD 缓存 DOM 引用、值不变不写；画布按面积限制 DPR~~（已完成，见第 9 章）；
3. 服务端增加 `rejected` 比例日志，把"反作弊误杀"变成可观测指标。

## 9. 架构审核回应（v2.1）

针对外部架构审核提出的 6 个盲区 + "144Hz 联机掉到 30Hz" 的归因，逐条核对代码后的结论如下。

### 9.1 采纳并已实施

| 审核项 | 结论 | 实施内容 |
|---|---|---|
| HUD 每帧 72 次 `querySelector` + 约 160 次 DOM 写 | **成立**，144Hz 下不可忽视 | 行内子节点一次缓存（`rowRefs`）、`setAttr/setStyle/setDisplay` 脏检查、整体降频到 **12.5Hz** |
| 4K/Retina 画布像素面积过大 | **成立** | `RENDER_DPR_MAX = 1.5`；新增 `__gp.perf.canvas` 暴露实际像素数 |
| `peer_state` 每包即时转发导致 O(N²) 发包 | **成立** | 服务端改为 **16ms 合包广播** `peers_bundle`，8 人房发送 3360 次/秒 → ≈60 次/秒；客户端新增解析（旧 `peer_state` 保留兼容）。**已用 `remote-smoothness.mjs` 端到端验证**：144Hz 采样 702 帧，观战速度 60.4 m/s（真值 60），波动 4.5% |
| 延迟残影 + 非对称硬碰撞（撞空气、贴车连罚） | **成立** | 动量损失按穿透深度缩放 + 150ms 冷却；对"明显滞后"的残影（`netAge>120ms` 或 `extra>120ms`）只做位移分离、不扣速度 |
| 非均匀 Catmull-Rom 在掉帧间隔下过冲 | **部分成立**（现版本已做非均匀缩放，但仍用邻点差分求切线） | 切线改为**样本自带速度向量**（时间参数化 Hermite，`m = (cos a, sin a)·v·span`），并加弦长 2.2 倍限幅；静止/缺 `v` 时回退邻点差分 |
| 生产 IP / root 路径出现在面向外部的文档 | **成立** | 本文档已脱敏为 `<PROD_HOST>` / `<APP_DIR>` / `<WEB_DIR>`，实际值仅存于本机 `.deploy/README.md`（gitignore） |

### 9.2 核对后不成立

**"144Hz 下 `advanceNetSim` 产生空帧跳步，且镜头被双倍推进"** —— 不成立。

- `steps = Math.max(1, Math.ceil(gap / MAX_SUBSTEP_DT))`，`Math.max(1, …)` 保证**每帧至少 1 步**；
- `stepDt = gap / steps`，因此单步推进量恒等于本帧真实间隔；
- `netSimAccum` 只在真正推进时累加（`gap > 0`），`visualDt` 取该累计值，不存在"按 `dt` 走一次、再按累计值走一次"。

实测数据（按 144Hz/60Hz/掉帧 三种间隔代入同一段逻辑）：

| 帧间隔 | steps | 物理推进 | 画面推进 |
|---|---|---|---|
| 6.94ms（144Hz） | 1 | 6.94ms | 6.94ms |
| 16.7ms（60Hz） | 1 | 16.7ms | 16.7ms |
| 50ms（掉帧） | 2 | 50ms | 50ms |

三者一致，说明自车物理与镜头**始终同源**。远端车同理：`interpolateRemoteCars(dt)` 就在同一次 `update()` 里逐帧执行，144Hz 下每帧都会在服务器 30Hz 的两个关键帧之间插值，"远端车被绑死在 30Hz"不成立。

因此"单人 144Hz、双人 30Hz"的差异只能来自**真实帧耗时**（8 车绘制 + 计时塔 DOM + 大画布 + 粒子），本轮按 9.1 的三项（HUD / DPR / 合包）先行压下；若仍未回到满帧，下一步是把在线模式改为"定时器固定 60Hz 模拟 + rAF 只渲染"。

### 9.3 已知取舍（不打算做）

- **反作弊的弯道/横向加速度校验**：本作以内网/自娱部署为主（`race_finish` 仍有合理性校验与排行榜下限），暂不引入曲率/边界模型；
- **服务端回放式 lag compensation**：竞速不需要 hitscan 级回滚，软化的幽灵碰撞已能消除主要体感问题。
